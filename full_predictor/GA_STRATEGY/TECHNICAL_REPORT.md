# GA_STRATEGY Technical Report

**Implementation snapshot: 21 November 2026**

## Abstract

GA_STRATEGY is a historical strategy research system that compares parameterized technical trading strategies with rules generated through genetic programming. It trains on past price data, selects strategy and risk parameters, evaluates subsequent months, and supports replay into a portfolio with shared capital. Its principal recent changes are transaction-charge-aware scoring, joint stop-loss and take-profit optimization, and preservation of selected settings through monthly evaluation and portfolio replay.

The current system supports reproducible experiments; its simulations do not establish live profitability. The parameter optimizer is an exhaustive grid search despite the GA name. The GP optimizer performs evolutionary rule search. Their scoring engine and the portfolio engine use different fill assumptions, which materially affect comparability.

## 1. Research objective

The system asks whether periodically retrained strategies can deliver useful out-of-sample returns after execution costs while controlling drawdown. It separates three decisions:

1. Which parameters and risk settings work best for each strategy on the training window?
2. Which strategy should a stock follow during the next evaluation month?
3. Which stocks should receive shared portfolio capital, based on preceding monthly performance?

A strategy is a rule producing a desired position. Optimization selects among rules or parameters. Execution converts desired positions into whole-share trades and account returns. Keeping these concepts separate is essential: a good training score does not guarantee a good portfolio outcome.

## 2. Data and preparation

The input is processed Parquet data generated by the project's feature-engineering pipeline. The loader expects a unique, nonmissing DatetimeIndex, OHLCV columns, and quality fields including `is_valid_bar`, `is_missing_bar`, and `segment_id`. Features include RSI, Bollinger bands, Donchian channels, rolling VWAP and moving averages.

The loader sorts timestamps, rejects invalid timestamp indexes and retains observed valid bars. If an imputed bar occurs within a segment, subsequent relevant indicators in that segment are masked to avoid using features contaminated by retrospective filling. These safeguards reduce one source of unreliable backtest signals; they do not certify the complete dataset against leakage, corporate-action errors or selection bias.

Indicators are primarily precomputed, so repeated searches can reuse their columns. The availability of a feature depends on its lookback and segment boundaries. Missing features must not be interpreted as valid trading signals.

## 3. System architecture

```text
Historical OHLCV -> feature engineering -> processed Parquet
                                              |
                         parameter search and GP rule evolution
                                              |
                            training-only risk optimization
                                              |
                         charge-aware execution and scoring
                                              |
                       next-month evaluation for every stock
                                              |
                       monthly reports and compounded curves
                                              |
                        trailing-month stock qualification
                                              |
                       shared-capital portfolio simulation
```

| Component | Main responsibility |
| --- | --- |
| `main.py` | Load data and run single-stock experiments |
| `config/strategies.json` | Indicator parameters and their candidate values |
| `engine/ga_optimizer.py` | Exhaustively compare parameter combinations |
| `engine/gp_optimizer.py` | Evolve and evaluate Boolean trading rules |
| `config/risk.json`, `engine/risk.py` | Risk search space and signal-level exits |
| `engine/execution.py` | Whole-share scoring account and fee-adjusted returns |
| `engine/fees.py` | Transaction charge calculations |
| `engine/backtester.py`, `engine/objectives.py` | Performance metrics and objective formulas |
| `batch.py` | Monthly multi-stock training, evaluation and reporting |
| `portfolio.py` | Stock qualification, funding, fills and portfolio accounting |

## 4. Parameterized strategies

Four configured strategy families are evaluated: VWAP mean reversion, RSI mean reversion, Bollinger-band reversion and Donchian-channel breakout. Their tunable inputs include indicator periods, entry thresholds, band widths and trend-filter periods.

The optimizer enumerates every combination in the configured indicator grid and combines it with every configured risk pair. It evaluates candidates on training data and retains the highest finite objective score. Held-out data is subsequently evaluated using those saved parameters.

The implementation does not evolve a population of numeric parameter chromosomes. Calling this part an exhaustive parameter search is more precise than describing it as a genetic algorithm. Its advantage is complete coverage of the specified grid; its limitation is that results depend on the grid boundaries and resolution.

## 5. Genetic programming

GP searches the structure of trading rules. Leaves compare a feature with a threshold, while internal nodes combine Boolean results using AND or OR. The current feature vocabulary uses RSI and Bollinger-position inputs.

An illustrative rule is:

```text
(RSI14 < 30) AND (BollingerPosition20 < 0.25)
```

This is an example of the grammar, not a reported winning strategy. A true rule requests a long position; a false rule requests cash, subject to risk exits.

The default population contains 40 candidates and evolves for 12 generations. Tournament selection favors higher-scoring parents. Subtree crossover replaces part of one rule with part of another; mutation can introduce a newly generated subtree. Two elites survive between generations, tree depth is bounded, and a new random candidate helps maintain exploration. Repeated trees reuse cached fitness.

For each unique tree, all nine risk pairs are evaluated. Its best training score is reduced by a complexity penalty of 0.01 per tree node. Thus the system evolves rule structure while using a nested grid search for risk settings. The RSI baseline also receives training-only risk tuning. Batch compares strategy winners using the shared unpenalized training objective.

## 6. Stop loss and take profit optimization

The shared default risk grid is:

| Variable | Values |
| --- | --- |
| Stop loss | 0.5%, 0.75%, 1.0% |
| Reward divided by risk | 1, 2, 3 |
| Take profit | Stop loss multiplied by reward-to-risk ratio |

For example, a 0.75% stop with ratio 2 gives a 1.5% target. TP is derived rather than independently searched, avoiding redundant parameter combinations. Each selected result saves `stop_loss`, `take_profit`, and `risk_reward_ratio`.

Risk is measured as price movement from the signal entry reference, not as a percentage of total portfolio equity. Thresholds are checked against observed closes. A threshold crossing can exit beyond its nominal level, and fees reduce the realized reward-to-risk ratio. After an SL or TP exit, the signal remains at cash until the raw target changes or a new session begins. Daily liquidation resets the entry reference.

The default nine pairs increase candidate evaluations roughly ninefold. This extension does not optimize trailing stops, maximum holding duration, allocation, or leverage. Those are separate potential experiments, not implemented search dimensions.

## 7. Execution and transaction charges

The scoring engine begins with 1,000,000 currency units and allocation 0.12 by default. For Indian-equity experiments this represents ₹10 lakh with a 12% allocation. Quantity is rounded down to whole shares, with entry fees considered in affordability. Quantity remains fixed while a position is held.

The current engine also accepts leverage from 1 to 5. Entry notional is scaled by leverage, and funding uses its margin assumptions. This supersedes older documentation describing scoring as exclusively unleveraged. Every comparison must record leverage and allocation because both affect returns and fees.

For India sessions, entries are restricted to before 15:00 and positions are forced out at or after 15:15, or at the last observed daily bar if earlier. Scoring fills occur at observed closes. It assumes fills succeed and does not simulate circuit-blocked exits.

The code includes a US fee branch and alternate session timing. It currently infers that branch from whether observed local clock times extend beyond 15:30, rather than explicit exchange metadata. Incorrect time zones or truncated sessions can therefore select an incorrect fee or timing model. Indian and US experiments should be separated and checked accordingly.

Indian charges are calculated by the shared FYERS helper, including brokerage, STT, exchange charges, SEBI, IPFT, stamp duty and GST. These are transaction charges, not income tax on profits. The encoded tariff is labeled 16 November 2026; historical evaluations apply this scenario rather than a date-specific tariff schedule. Report calculations use component-level paise rounding; optimized scoring also has a faster fee path. Agreement between those paths is an important accounting invariant.

A reversal incurs closing and opening orders. Daily and terminal liquidations incur fees. Fees are already incorporated into account returns and must not be deducted again.

## 8. Performance metrics and objectives

Let E(t) be account equity after valuation and charges at bar t. Bar return is E(t)/E(t-1) - 1, with starting capital used before the first bar. Daily and cumulative returns compound the corresponding bar returns.

| Metric | Definition used by the system |
| --- | --- |
| Cumulative return | Product of one plus bar returns, minus one |
| Sharpe | Mean daily return / sample daily standard deviation × square root of 252 |
| Sortino | Mean daily return / root mean square of negative daily returns × square root of 252 |
| Maximum drawdown | Most negative equity/running-peak minus one, including initial capital as a peak |
| CAGR | Compounded growth annualized over actual elapsed timestamp time |
| Calmar | CAGR / absolute maximum drawdown |

Sharpe does not subtract a risk-free rate. Nonnegative days contribute zero in the Sortino downside average. Undefined or nonfinite inputs are excluded from optimization. Zero drawdown makes Calmar undefined under the current implementation.

The selectable objectives are:

```text
blend = 0.7 Sharpe + 1.3 Sortino + 0.5 dd
calmar = CAGR / abs(dd)
composite = 0.5 Sharpe + 0.8 Sortino + 2 dd - 5 dd²
            + 0.4 min(Calmar, 2)
```

Here dd is negative, and `blend` remains the default. Calmar rewards annualized return relative to drawdown; it is not a hard drawdown limit. A higher training objective must still be tested out of sample.

## 9. Monthly walk-forward evaluation

The default batch schedule reserves the first six calendar months for training and evaluates the next month. The window then moves forward by one month, retrains, and evaluates the following month. For example, January–June fits July, then February–July fits August.

Training candidates start with fresh scoring accounts. Out-of-sample accounts retain their own ending capital across evaluation months. Each strategy and the monthly `Selected` strategy maintain separate capital histories. `Selected` follows the training winner, not the strategy that later earned the highest test return.

Because Selected and individual strategy accounts can have different balances, whole-share rounding and brokerage caps can cause different percentage returns even when their signals match. Full-history curves concatenate monthly after-charge returns and compound them. Validation labels in batch identify initial evaluation months; the winner is still selected from training results.

Rolling retraining reduces dependence on a single fixed fit but does not remove overfitting. Repeatedly choosing the best of many candidates can exploit training noise. Hyperparameter decisions made after inspecting evaluation results can also contaminate the research process.

## 10. Portfolio construction

The portfolio stage ranks stocks by the compounded return of their Selected strategy over preceding complete calendar months. The default lookback is three months and the default eligible universe is the top ten stocks. The current month's returns are excluded. Missing histories are excluded; a minimum number of available candidates is also required.

This ranking is based on trailing return even when the training objective is Calmar. Strategy optimization and stock ranking are separate decisions.

The portfolio replays saved parameters into a shared-capital account. Its default allocation is 4%, unlike the scoring engine's 12%. Portfolio flags support different allocations, leverage and notional-versus-margin sizing. It uses its own next-open execution, circuit restrictions, deferred exits and delivery/funding handling. Sharing the charge helper does not make its results identical to scoring results.

## 11. Outputs and reproducibility

Batch exports monthly results, stock/strategy summaries, stock rankings, per-stock cumulative charts and daily cumulative-return tables. Saved parameter JSON includes the risk settings needed for replay. Reports expose capital, final equity, fees, charge components, fills, exposure, returns and risk metrics.

Exposure fields measure the fraction of observed bars ending with a direction; they are not average capital utilization. Cost drag is fees divided by starting capital for the reporting period. Position changes in execution reports count fills, so a complete round trip normally counts twice.

From the `full_predictor` directory, a small reproducible experiment can be started with:

```powershell
python -m GA_STRATEGY.batch --limit 5 --years 5 --workers 4 --objective blend --output reports/risk_blend
python -m GA_STRATEGY.batch --limit 5 --years 5 --workers 4 --objective calmar --output reports/risk_calmar
```

For a controlled comparison, explicitly specify the same stock list, date range, data snapshot, GP seed, population, generations, allocation, leverage and risk grid. Separate output folders preserve experiment provenance. Existing reports do not automatically acquire new risk or fee behavior; retraining is required.

## 12. Validation and evidence status

On 21 November 2026, the focused risk-optimization, execution and portfolio test suites completed successfully: **18 tests passed**. They cover behaviors including risk-grid construction, session resets, saved GP risk settings, training-only choice reuse, joint parameter search, fees, monthly compounding, stock qualification and portfolio accounting.

These checks establish specific software behaviors. They do not establish economic performance, comprehensive leakage prevention, or production readiness. This report does not present historical returns from earlier configurations as measured results of the new risk-optimized engine. A new full-history comparison is required for performance claims.

## 13. Limitations and next experiments

The most material modeling limitation is same-close scoring versus next-open portfolio execution. Stops are tied to signal entry references rather than actual portfolio fills, so a nominal SL is not a guaranteed realized loss limit. Early exits on the last available daily bar assume knowledge of where the data ends. Spread, market impact and partial fills are not fully modeled.

The timing heuristic should be replaced with explicit exchange/session metadata before combining markets. Corporate-action handling, historical constituent selection and feature causality require independent dataset audits. Larger search spaces increase selection bias as well as computation.

A controlled evaluation should compare fixed default risk with optimized risk under each objective using identical data and costs. Report out-of-sample CAGR, drawdown, net profit, fees, trade count, turnover and monthly consistency. Preserve a final untouched period, examine parameter stability across months, and repeat GP with multiple seeds. These are proposed experiments, not completed findings.

## Conclusion

The updated GA_STRATEGY combines indicator parameter search, evolutionary rule construction, training-only risk optimization and charge-aware monthly evaluation. Its main benefit is a traceable route from a candidate rule to saved settings, out-of-sample returns and portfolio replay. The next evidence needed is a controlled fresh backtest that separates the effects of risk optimization, fees, sizing and execution assumptions.
